About me

Most data migrations look tidy on a diagram. The reality is old logic, undocumented joins, duplicate metrics, and reports people still depend on. The hard part is understanding a sparsely documented legacy system well enough to rebuild it without reproducing its problems.

I work across BI and analytics, data architecture and semantic modelling, with applied AI on top. I design dimensional models with conformed dimensions and governed semantic layers that non-technical colleagues can self-serve from safely, set the standards the people building on them work to, and use SQL to understand and validate what the source systems actually contain.

The habit that runs through all of it is not trusting outputs I haven't audited. I use LLMs to untangle undocumented legacy logic, then validate every result against the source systems. Building a Voice-of-Customer risk pipeline on SQL Server vector search, I hand-labelled the retrieved matches and measured precision and recall rather than assuming similarity meant relevance.

Currently at ACO Technologies, acting as technical authority for the client side of our Microsoft Fabric migration — target architecture, capacity design, the build specification our external engineering partner delivers against, and final sign-off for go-live readiness. Alongside that I own the existing Azure platform and the Power BI estate.

Rebuilding a legacy estate into a dimensional model — in public

A step-by-step record of taking a legacy "one table, append everything" reporting estate apart and rebuilding it properly: agreeing with the business what is actually used, removing what isn't, then reverse-engineering which columns belong to which entity — and which belong to several. The result is multiple fact tables sharing conformed dimensions, which is where the real difficulty sits: getting separate facts to agree on the same dimensions at the same grain. Work in progress, published as I go.

Not every Fabric error is a Fabric problem — linking Dynamics 365 to Fabric

Mirroring Dataverse into Fabric is cheaper and less error-prone than building ingestion by hand, so it was the right call for our Dynamics 365 data. Getting the link working was another matter. Three failures, each with an error message pointing somewhere other than the cause: a Power BI licence error that was really a missing Dataverse System Administrator role; an "unauthorized" error that was the Fabric service principal lacking read access to the tables; and a region mismatch — Fabric capacity in West Europe, Dataverse in the UK — which the link will not cross. Solved with a small F2 capacity in the UK dedicated to the link, rather than moving the whole platform.

Row-level security when roles filter on different dimensions

Most RLS examples give every role the same filter with different values. This one doesn't: different roles restrict on different dimensions — by location, by restaurant, and by location/restaurant combination — all against the same data. A user-to-role bridge lets one person hold several roles at once, which is where it usually breaks, because the filters have to combine additively rather than intersecting into nothing. Built with USERPRINCIPALNAME() and RELATEDTABLE(), and explained end to end in a four-part series.

VoC Risk Scorecard — trust-audited vector search on SQL Server

Built live for the Microsoft SQL AI Promptathon (July 2026). A rerunnable notebook that connects to SQL Server and recomputes a per-SKU customer-risk scorecard from reviews, support chats, tickets and sales. The distinctive part: instead of trusting vector similarity, it audits it — hand-labelling retrieved matches to measure precision and recall, surfacing the failure modes a naive pipeline would hide. Two independent methods converged on the same at-risk product.
